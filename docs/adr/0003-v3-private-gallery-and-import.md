# ADR 0003: local gallery, private photo conversion and offline Web packaging

Status: implemented in source; runtime/CI/device verification is pending.

The owner explicitly requests continued development without local tests/builds or waiting for CI. This change advances V3 while prior device/release gates remain open. Android Actions stays manual-only. Persian remains the default, with all new screens and errors translated into English.

## Catalog and private library

The bundled catalog contains 40 original geometric pictures. Existing V2 level files, IDs, content versions and checksums are retained. `metadata.json` adds categories/tags separately from the immutable schema-2 levels. `CatalogMetadataRepository` permits replacing the asset metadata adapter later without changing the painting engine. `tool/generate_catalog.py` records the source of the 30 added geometric designs and does not overwrite existing versioned images.

`ArtworkRepository` persists an independent schema-1 library under `pixelhub.library.v1`. It holds favorites and at most 20 private artworks, each with a UUID, UTC creation date, conversion parameters and a full checksummed schema-2 level. The original photo, file name, EXIF/GPS data and external photo references are never persisted. Personal names use the entered text in both languages; the unnamed fallback is bilingual.

Progress remains in the V2 per-level/version records. In-progress/completed views derive from stored snapshots and active sessions; the painting screen still reports whether writes are acknowledged. A corrupt library is retained until explicit data-clear confirmation. Failed library writes preserve the previous in-memory library and can be retried. A UTF-8 2 MiB document cap limits storage growth, but browser quota/eviction and failed writes remain possible. No storage encryption or cloud backup is claimed.

Deletion writes the reduced library before removing its separate progress key. A failed second operation can leave an unreachable progress record; a later confirmed clear removes all Pixelhub keys. Clear removes only `pixelhub.*`, retains bundled resources, and waits for session/language writes before clearing. A partially failed clear reloads remaining data and reports failure.

## Converter

Android uses the Storage Access Framework through `file_selector`; no broad gallery/storage permission is added. Web uses a local file input. JPEG, PNG and WebP are accepted, with a 12 MiB encoded cap, 12 million pixels, at most 6000 pixels per dimension and one frame. Headers are inspected before decoding a full frame. HEIC, SVG and animated inputs are outside this version.

EXIF orientation is baked, the working image is reduced to at most 1024 pixels on its longest side, transparent pixels are composited on white, and a fresh RGB PNG removes metadata. Crop and 90-degree rotations operate on this normalized image, with an explicit physical left/right/up/down crop offset independent of RTL text direction.

Easy/normal/hard generate 32/64/128 square grids, with adjustable 2–24 maximum colors. Area resizing, a bounded RGB histogram, weighted median-cut and nearest-color assignment generate deterministic opaque palettes without dithering. Unused palette entries are removed. Conversion returns the same schema-2 `LevelDefinition` used by the engine; content is saved before opening its painting route.

Native `compute` moves conversion to an isolate. Flutter Web's `compute` executes on the UI isolate, after showing the busy state. Web can briefly pause during processing; no Web Worker, timing, responsiveness or low-memory performance result is claimed. Processing-memory measurements and real-device validation remain pending.

## Export and offline resources

Completed pictures expose PNG export at an integer nearest-neighbor scale, at most 1024 pixels on the longest side. Android uses the platform share sheet through `share_plus`; Web downloads a Blob URL and releases it later. Sharing is user-initiated. No public posting or image upload is introduced.

Android bundles all catalog resources. Web builds include a custom service worker plus a content-hashed offline manifest generated by `tool/prepare_offline_web.py`. Installing caches public app files, local fonts, CanvasKit and bundled levels as one version. Photos, localStorage and Blob exports never enter that cache. Cached navigation/resources stay with the active artifact; updates wait for previous tabs to close, avoiding a forced mid-paint reload. Two artifact caches are retained per scope. Cache installation failures do not prevent online play and are shown with retry in Settings. Service worker readiness is tracked, but browser eviction still removes offline resources.

The first Web visit needs connectivity. Offline reopening requires successful production cache preparation, HTTPS or localhost, and retained browser data. The development Web server lacks the generated manifest, so its offline status is expected to be unavailable. These behaviors have not been exercised for V3 in this session.
