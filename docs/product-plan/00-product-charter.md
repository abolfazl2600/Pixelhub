# 00 | منشور محصول Pixelhub

## مسئله‌ای که حل می‌کنیم
کاربر می‌خواهد بدون نیاز به مهارت هنری، تصویر شماره‌دار را با لمس رنگ کند، تصاویر خود را به مراحل Pixel Art تبدیل کند و همان تجربه را در اپ Android و وب داشته باشد. محصول باید سریع، روان، لذت‌بخش و بدون تبلیغ اجباری وسط رنگ‌آمیزی باشد.

## مخاطب و ارزش پیشنهادی
- مخاطب اولیه: علاقه‌مندان به بازی‌های Casual، نقاشی شماره‌ای و پیکسل‌آرت.
- ارزش اصلی: شروع فوری بدون حساب، پیشرفت قابل مشاهده با هر تعامل، قابلیت ادامه کار، تولید مرحله از عکس شخصی.
- وجه تمایز پیشنهادی: UI مشترک وب/اندروید، تجربه آرام و تبلیغات اختیاری، پشتیبانی خوب از آفلاین، تبدیل عکس با کنترل سطح دشواری.
- کشورها/سن هدف: پیش از انتشار عمومی تعیین و مستند شود. در صورت هدف‌گیری کودکان، سیاست‌های فروشگاه و تبلیغات کودکان دوباره بررسی شوند.

## محدوده قطعی
- Android اولویت اول تست و بهینه‌سازی است.
- Web همان صفحه موبایل (Mobile-first fixed composition) است: قاب منطقی عرض 360–430، وسط‌چین در دسکتاپ، بدون چیدمان دسکتاپ جایگزین.
- یک کد Flutter برای منطق و UI؛ پیاده‌سازی‌های مخصوص پلتفرم پشت Interface / Adapter.
- مراحل رسمی با داده JSON/باینری نسخه‌بندی‌شده؛ عکس‌های شخصی به‌صورت خصوصی و روی دستگاه پردازش شوند مگر کاربر صریحاً انتشار ابری بخواهد.
- تولید APK/AAB و Web در GitHub Actions و امکان میزبانی استاتیک وب در GitHub Pages.

## خارج از هدف بلندمدت فعلی
- شبیه‌سازی برند، آثار و فایل‌های بازی رقیب.
- اپ دسکتاپ اختصاصی یا UI دسکتاپ جداگانه.
- نیاز اجباری به ثبت‌نام برای رنگ‌آمیزی اولیه.
- الزام به اتصال دائمی اینترنت برای محتوای دانلودشده.
- سرور زنده یا داشبورد با GitHub Pages؛ این سرویس فقط سایت استاتیک میزبانی می‌کند.

## فرض‌های راهبردی قابل بازنگری
- Flutter/Dart برای Android+Web؛ اگر نمونه V2 در مرورگر یا گوشی هدف ضعیف بود، قبل از V3 ADR ثبت و راه‌حل فنی بازنگری شود.
- Backend پیشنهادی از V4/V5: NestJS + PostgreSQL + Object Storage؛ آغاز پروژه بدون سرور کاملاً امکان‌پذیر است.
- پنل مستقل Next.js در V5؛ بدون پرداخت و Community در MVP.
- محیط اجرا ابتدا کنترل هزینه؛ Microservice و Kubernetes تا وقتی نیاز اندازه‌گیری نشده ممنوع.
- راه‌اندازی Community فقط با ابزار گزارش، حذف و مسدودسازی و نیروی نظارت محتوا.

## تجربه کاربری و اصول طراحی
1. کاربر کمتر از چند تعامل به اولین نقاشی برسد.
2. هر تصویر یک نوار پیشرفت، پالت قابل فهم و امکان ادامه‌دادن داشته باشد.
3. تمام تعاملات لمس در Android و Pointer/Mouse در Web آزموده شوند.
4. متن و کنترل‌ها در سایزهای کوچک خوانا باشند؛ قاب ثابت به‌معنای غیرقابل‌استفاده‌بودن نیست.
5. برای اتصال قطع‌شده پیام روشن نمایش دهیم، اما نقاشی محلی را متوقف نکنیم.
6. شکست پردازش عکس بدون از دست رفتن عکس و پیشرفت فعلی مدیریت شود.
7. پایان بازی باید قابل اشتراک و فهم باشد، بدون جبران با Popup مزاحم.

## تعریف کیفیت محصول
- سرعت و ثبات مهم‌تر از تعداد زیاد امکانات نمایشی‌اند.
- کرش، حذف پیشرفت، خرابی سطح‌ها و عدم توانایی نصب APK نقص بحرانی است.
- هیچ نسخه‌ای بدون معیار پذیرش و لاگ تست به «کامل» تغییر وضعیت نمی‌دهد.
- فهرست دسترسی‌های پلتفرمی و سیاست‌های حریم خصوصی با نسخه منتشرشده همخوان باشند.

## نقشه ریسک و اقدام
| ریسک | پیشگیری |
|---|---|
| Flutter Web برای Canvas سنگین کند شود | Performance spike در V2 و Rendering benchmark پیش از تصمیم V3 |
| GitHub Pages مسیرهای داخلی را 404 دهد | استفاده از Hash-based routing در صفحات اولیه یا Hosting با SPA fallback |
| پاک‌شدن داده مرورگر | هشدار Guest، Export/Backup اختیاری، Sync در V4 |
| عکس خصوصی کاربر ناخواسته آپلود شود | پردازش و ذخیره محلی به‌طور پیش‌فرض؛ opt-in دقیق |
| تصاویر منتشرشده حق‌نشر نداشته باشند | ثبت Attribution/License و روند تأیید در Admin |
| افزایش هزینه پردازش تصویر | پردازش محلی، Worker جدا برای تصاویر محتوایی |
| فروشگاه انتشار را رد کند | بررسی Data Safety، Target API، Billing و سیاست‌ها در V6 |
| AI تعداد زیادی فایل نامعتبر تولید کند | تغییرات کوچک، تست CI، بازبینی و release gate |

## تعریف موفقیت

V2: نقاشی با عملکرد روان و ذخیره بازی.
V3: عکس شخصی قابل تبدیل و رنگ‌آمیزی و کاتالوگ محلی.
V4: شروع روی Android و ادامه روی Web با یک حساب.
V5: افزودن مرحله از پنل بدون آپدیت اپ.
V6: انتشار قابل اتکا و خریدهای معتبر در بازار هدف.
V7: Community امن و پایدار با توان عملیات روزانه.
